# Асинхронная диспетчеризация экстренных оповещений (Webhook/Telegram) и изолированный режим тестового прогона правил (Dry-Run)

## Контекст и постановка задачи

Во втором раунде переговоров Заказчик добавил критически важное требование (`SYS-10`): при срабатывании аварийного правила (например, перегрев `temperature > 28 °C` или датчик движения в закрытой зоне) система **IoTPanel** должна не только переключить исполнительное устройство (`POST /command`), но и мгновенно отобразить красный баннер тревоги на экране оператора, отправить уведомление в Telegram / корпоративный Webhook дежурной смене, а также предоставить инженеру кнопку «Тестовый прогон правила (Dry-Run)» без реального включения промышленного оборудования. Как спроектировать подсистему оповещений и тестового прогона, чтобы задержки внешних мессенджеров не замедляли переключение реле (`< 1 с`) и чтобы разработку можно было распараллелить между Middle- и Junior-разработчиками без сдвига дедлайна?

## Драйверы решения

* **Неблокирующее выполнение команд (`BG-2`, `REQ-PERF-002`):** время отправки `POST /command` на устройство не должно зависеть от скорости ответа внешних серверов Telegram или корпоративного вебхука.
* **Безопасность тестового прогона (`SYS-10`):** режим `Dry-Run` должен проверять условие правила и доставку уведомлений, но гарантированно исключать подачу физического сигнала на эмулятор оборудования.
* **Соблюдение жёсткого дедлайна (4 недели):** архитектура должна позволять поручить клиентский UI-баннер тревоги Junior-разработчику ($10/ч), а серверный диспетчер уведомлений — Middle-разработчику ($25/ч).

## Рассмотренные варианты

* **Вариант 1:** Синхронный вызов внешнего Webhook/Telegram API непосредственно внутри цикла проверки телеметрии `RuleEvaluator`.
* **Вариант 2:** Опрос таблицы логов внешним cron-скриптом раз в минуту для отправки уведомлений.
* **Вариант 3:** Асинхронный серверный модуль `AlertDispatcher` с неблокирующей очередью повторов (Retry Queue), WebSocket-событие `CRITICAL_ALERT` для UI-баннера и выделенный эндпоинт `POST /api/rules/dry-run` с флагом `isDryRun = true`.

## Итог решения

Выбранный вариант: **«Вариант 3: Асинхронный модуль AlertDispatcher + WebSocket-событие CRITICAL_ALERT + эндпоинт Dry-Run»**, потому что он полностью изолирует критический контур управления оборудованием от сетевых задержек внешних вебхуков и позволяет независимо разрабатывать серверную и клиентскую части силами двух разработчиков.

### Последствия

* **Хорошо**, потому что переключение реле (`POST /command`) выполняется мгновенно (`< 150 мс`), а отправка сообщения в Telegram происходит асинхронно в фоне с 3 попытками повтора при сбое связи.
* **Хорошо**, потому что разделение на серверный эндпоинт (`SYS-10 Backend`, 16 ч, Middle) и клиентский компонент `CriticalAlertBanner` (`SYS-10 Frontend`, 8 ч, Junior) позволило сохранить 4-недельный дедлайн проекта и уложиться в бюджет $3 450.
* **Плохо**, потому что при переполнении очереди в случае длительного отсутствия внешнего интернета старые уведомления требуют ротации в памяти сервера.

### Подтверждение

Верифицируется двумя автотестами:
1) Вызов `POST /api/rules/dry-run` должен создавать запись в журнале с пометкой `DRY-RUN` и рассылать фрейм `CRITICAL_ALERT`, при этом счётчик вызовов `POST /command` на эмуляторе обязан оставаться равным `0`;
2) Искусственная задержка ответа тестового вебхука на 3 секунды не должна увеличивать время выполнения команды переключения реле (`< 1000 мс`).

## Плюсы и минусы вариантов

### Вариант 1: Синхронный вызов Webhook внутри RuleEvaluator

* **Хорошо**, потому что реализуется несколькими строками кода без очереди задач.
* **Плохо**, потому что при зависании внешнего API Telegram на 3–5 секунд блокируется весь поток обработки телеметрии и нарушается требование `BG-2` (`<= 1 с`).

### Вариант 2: Опрос БД внешним cron-скриптом раз в минуту

* **Хорошо**, потому что не нагружает основной процесс сервера Node.js.
* **Плохо**, потому что задержка оповещения в 60 секунд неприемлема для критических аварий (перегрев, проникновение).

### Вариант 3: Асинхронный AlertDispatcher + WebSocket CRITICAL_ALERT + Dry-Run API

* **Хорошо**, потому что обеспечивает мгновенную индикацию аварии в браузере по WebSocket (`< 100 мс`) и гарантированную доставку вебхуков без блокировки основного потока.
* **Хорошо**, потому что флаг `isDryRun` в `RuleEvaluator` позволяет безопасно тестировать правила прямо из конструктора правил.

## Дополнительная информация

Решение принято по итогам второго раунда переговоров с Заказчиком. Связанные требования: `BG-1`, `BG-3`, `REQ-FUNC-014`, `REQ-OBS-002`. Элементы дизайна в SDD: `DV-01-Composition`, `DV-03-Interface`, `DV-05-Algorithm`, системная функция `SYS-10`.
