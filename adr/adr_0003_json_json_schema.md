# Сериализация и валидация правил автоматизации на основе JSON Schema (Ajv) и PostgreSQL JSONB

## Контекст и постановка задачи

До внедрения системы **IoTPanel** инженеры редактировали правила автоматизации вручную в текстовых JSON-файлах и регулярно допускали синтаксические ошибки. Бизнес-цель `BG-3` требует полностью исключить ошибки синтаксиса и сократить время настройки правила до 30 секунд за счёт 4-шаговой формы: «Выбрать устройство -> Выбрать метрику -> Условие -> Действие» (`REQ-FUNC-007`, `REQ-FUNC-008`). Какой механизм валидации и формат хранения в БД выбрать для гарантии целостности правил?

## Драйверы решения

* **Нулевой процент синтаксических ошибок (`BG-3`, `REQ-FUNC-008`):** невозможность сохранить невалидный JSON-объект правила ни через UI, ни через прямой вызов API.
* **Скорость создания правила (`<= 30 с`):** мгновенная подсветка корректности заполнения 4 шагов и живой предпросмотр JSON-кода на экране.
* **Производительность выборки (`RuleEvaluator`):** быстрый поиск активных правил по `device_id` при поступлении телеметрии.

## Рассмотренные варианты

* **Вариант 1:** Хранение правил в текстовом поле `TEXT` и проверка регулярными выражениями.
* **Вариант 2:** Жёсткая реляционная таблица с отдельными колонками для каждого параметра без сохранения JSON-структуры.
* **Вариант 3:** Двойная валидация по единой схеме JSON Schema (библиотека `Ajv`) на клиенте и сервере с хранением канонического объекта в поле `JSONB` СУБД PostgreSQL 16.

## Итог решения

Выбранный вариант: **«Вариант 3: Двойная валидация через JSON Schema (Ajv) + хранение в PostgreSQL JSONB»**, потому что единая декларативная схема гарантирует идентичную проверку типов метрик, операторов (`>`, `<`, `==`, `!=`) и действий как в браузере, так и на сервере перед записью в базу данных.

### Последствия

* **Хорошо**, потому что синтаксические ошибки исключаются архитектурно: кнопка «Сохранить правило» активируется только при прохождении валидации схемы всех 4 шагов.
* **Хорошо**, потому что тип `JSONB` в PostgreSQL 16 позволяет сочетать строгую реляционную привязку к `device_id` с гибкой структурой полезной нагрузки правила (`rule_json`).
* **Плохо**, потому что при добавлении нового типа действия необходимо обновлять общий файл схемы `rule.schema.json`.

### Подтверждение

Проверяется модульными и API-тестами: отправка POST-запроса `/api/rules` с пропущенным полем `metric` или некорректным оператором должна детерминированно возвращать статус `400 Bad Request` без записи в таблицу `automation_rules`.

## Плюсы и минусы вариантов

### Вариант 1: Поле TEXT и регулярные выражения

* **Хорошо**, потому что не требует подключения внешних библиотек валидации.
* **Плохо**, потому что регулярные выражения не способны надёжно проверять вложенные типы данных и соответствие метрики выбранному устройству.

### Вариант 2: Жёсткие реляционные колонки без JSON

* **Хорошо**, потому что использует стандартные ограничения `CHECK` в SQL.
* **Плохо**, потому что нарушает требование `REQ-FUNC-008` о формировании и предпросмотре переносимого JSON-объекта правила для движка правил.

### Вариант 3: JSON Schema (Ajv) + PostgreSQL JSONB

* **Хорошо**, потому что библиотека `Ajv` компилирует JSON-схему в быстрый JavaScript-код, работающий одинаково в React и в Node.js.
* **Хорошо**, потому что позволяет реализовать режим тестового прогона `Dry-Run` (`SYS-10`) путём передачи объекта правила напрямую в `RuleEvaluator`.

## Дополнительная информация

Связанные требования из SRS: `BG-3`, `REQ-FUNC-007`, `REQ-FUNC-008`, `REQ-FUNC-010`, `REQ-SEC-003`. Элементы дизайна в SDD: `DV-02-Information`, `DV-05-Algorithm`, функции `SYS-04`, `SYS-05`.
